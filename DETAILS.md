# Fuselage — Technical Details

This is the technical companion to the README.md: a subsystem-by-subsystem breakdown of what's implemented, what's in progress, and what's still ahead.

---

## Working State (BUTTOCKS) 0.2 complete

**GDMF - Graphic Device Minimalist Framework** ("gdmf.h", "gdmf.c", "gdmf_vulkan.c"):
Window creation and management, Vulkan instance/device/swapchain bootstrapping, render pass, framebuffers, command pools, per-frame sync, and swapchain recreation on resize. Handles DPI awareness. The application never touches Vulkan directly. A shared per-swapchain-image palette buffer (`Colors[256][16]`, re-uploaded once per frame) is owned here and consumed by every palette-indexed subsystem below, rather than each maintaining its own redundant copy. VSync is toggleable at runtime (`GDMFSetVSync`/`FuselageSetVSync`), switching the swapchain between `VK_PRESENT_MODE_FIFO_KHR` and `VK_PRESENT_MODE_IMMEDIATE_KHR` (when the surface supports it).

**Text Layer** ("gdmf_textlayer.h", "gdmf_textlayer.c"):
An 80×45 text grid with 16×16-pixel cells. Features text rendering, cursor control, scrolling, per-cell color, and standard escape characters (`\n`, `\t`, `\r`) in every string-printing entry point. The character atlas (256 glyphs, packed at 2 bits per pixel) is embedded in "packedbitmaps.h" and generated by Edibima. Includes a full set of "tlPrint" functions. Rendered as a single full-screen quad with per-cell character/color data read from a storage buffer in the fragment shader, rather than one quad per character. This is a large rendering-cost reduction over the original per-cell-quad approach, even in the worst case where all 3600 cells change every frame. The engine draws the text layer automatically every frame (when enabled); the application only manages text state. This layer is for system and application level output (errors, warnings, etc.) and is not intended for game related text.

**Color Palette** ("colors.h", "colors.c"):
256 palettes, each with 16 registers/colors. Provides names for color lookups. Predefined color sets include grayscale, primary colors, retro-styled shades, C64, ZX Spectrum, ANSI, Tandy, and NES palettes.

**Sprite Layer** ("GDMF/gdmf_sprites.h", "GDMF/gdmf_sprites.c"):
Manages up to 640 sprites with position, scale, rotation, skew, a per-sprite hotspot (anchor point, which position places and rotation can optionally pivot about — it may sit outside the sprite so instances can move in unison about a shared point), transparency, priority, and an assigned color palette (256 slots x 16 colors each), decoupled from the bitmap atlas so many instances can share one shape. Bounding-box and pixel-level collision detection, per-instance flip, and genuine 256-level priority interleaving with tiles and pixies (drawn highest priority to lowest; at an equal priority the type order is pixies, then tiles, then sprites).

**Tile Layer** ("GDMF/gdmf_tiles.h", "GDMF/gdmf_tiles.c"):
A multilayered tile handling system (16 independent layers) supporting embedded tilesets and tilemaps, scrolling, wrapping, per-cell offsets, per-cell palette, and viewport control, dirty-tracked per swapchain image.

**Pixie Layer** ("GDMF/gdmf_pixies.h", "GDMF/gdmf_pixies.c") A programmable framebuffer unit with no ANUS equivalent. Three modes: Mode 0 ("call once, display forever"), an SVGA-framebuffer-style persistent RGBA output buffer (ideal for content that rarely changes); Mode 1, live, using no persistent buffer — commands become that frame's draw calls directly (ideal for content redrawn every frame); and Mode 2 ("mask"), an 8-bit coverage mask that governs the items at its own priority — those items are rendered offscreen and composited back through the mask, so layers already drawn behind them show through wherever the mask is set (polarity flippable via `SetPixieMaskInvert`). `PIXIE_OP_UNPACK` decodes PNG-derived assets packed by the companion PixiePacker tool (see below) directly into a Mode 0 pixie's output buffer.

**PixiePacker** ("tools/PixiePacker"):
A build-time-only CLI that packs a PNG into a compressed blob + C header, so the engine never needs a runtime image-decoding dependency. Auto-selects between palette-indexed and true-color formats depending on the source image's color count, and applies a stack of compression passes (RLE, an LZ77-style alternative to RLE (sliding-window back-reference matching), a delta/predictive filter for true-color gradients, and canonical Huffman) trying each combination automatically and keeping whichever compresses smallest per asset.

**Sprite/tile/asset conversion tools** ("spriteconverter.c", "tileconverter.c", "PixiePacker"):
Convert image data into Fuselage-compatible sprite/tile/pixie formats. Validate and generate palettes conforming to the 16-color-per-palette (or 256-color, for Pixie's own-palette tier) limit and output C-style header files.

*The build-time tools above (PixiePacker, the sprite/tile converters, and the Edibima atlas generator) are maintained as a separate set of files and will soon also be available on GitHub.*

**CAKE - Controller And Keyboard Events** ("CAKE/cake.h", "CAKE/cake.c"):
Raw input handling for keyboard, mouse deltas, XInput controllers, and HID controllers(WIP) with hotplug support. Full implementation on Windows; Linux and macOS stubs present for future ports.

## Working State (COLON, in progress)

**DICE - Timer** ("DICE/dice.h", "DICE/dice_timers.h", "DICE/dice.c", "DICE/dice_timers.c"):
Self-contained timing subsystem, unaware of Fuselage/GDMF/CAKE (same isolation CAKE has). Handle-based timers (`DICE_InitTimer`/`DICE_InitTimerInterval`, up to `DICE_MAX_TIMERS`), each supporting poll (`DICE_ConsumeTimer`, an atomic elapsed-interval counter) and an optional callback simultaneously rather than forcing a choice. Full `Start`/`Stop`/`Pause`/`Resume`. Windows backend uses one high-resolution waitable-timer thread per handle, re-armed each fire against a fixed-cadence target to avoid drift; Linux/macOS are stubs for now, matching CAKE's precedent. `fuselage.c` now drives its simulation (input + game logic) off DICE, decoupling simulation speed from rendering timing: game logic ticks at a fixed, configurable rate while rendering paces itself independently (vsync, or an optional frame-rate cap). This replaces the old flat `Sleep(1)` loop. There is deliberately no catch-up — a stall means the simulation falls behind real time rather than ever running game logic unthrottled. **DICE is fully usable now**: games can create their own timers alongside the ones Fuselage runs internally.

**DICE - RNG** ("DICE/dice_rng.h"):
Interface designed (WIP). Handle-based streams (up to `DICE_MAX_RNG`) in four flavors sharing one consumption API (`DICE_RandUint`/`Int`/`Float`/`Chance`) so a caller can't tell which flavor a handle is running as: `DETERMINISTIC` (locked-seed replay), `ENTROPY_SEEDED` (seeded once from OS entropy), `CONTINUOUS` (self-perturbing every draw), and `ACCUMULATE` (grows only via caller-supplied `DICE_MixRNGEntropy`).

## Building

Fuselage builds with **clang** and **make**. On Windows the reference toolchain is MSYS2's **ucrt64** environment, with the **Vulkan SDK** installed — the build reads the `VULKAN_SDK` environment variable to locate Vulkan's headers and libs, and falls back to system Vulkan packages (e.g. MSYS2's `vulkan-headers`/loader) when it is unset.

```
make debug     # console subsystem: printf/log visible in the terminal
make release   # windowed subsystem (-mwindows), stripped
```

Both targets produce `fuselage.exe` in the project root. Compiled shaders and packed assets are checked in as generated C headers, so an ordinary build needs no shader compiler or asset tools — those pipelines only run when a shader or source asset actually changes.

## Planned and Future Goals

**SHARP - audio subsystem:**
Planned audio output. Not yet started. (Estimated to begin around version 0.5)

**VPU - Virtual Processing Unit** (planned, 0.4 DERRIERE):
An interpreter for compiled RISC-V, letting games and system-level logic be written in assembly-like code. The executable blob it runs is a **ROAP** file (*Run On Any Platform*). The RISC-V program together with the set of `ecall`s that target Fuselage's subsystems form **MISL** — the layer that makes a ROAP worth running, since pure RISC-V with no way to reach Fuselage's features would have nothing to do. The VPU is entirely optional: every Fuselage component stays directly usable from C without it. The Pixie layer's opcode/args command packet already mirrors the RISC-V `ecall` convention in anticipation of this.

**FuselageInputHandler:**
A high-level input abstraction layer sitting between game code and CAKE. Will expose human-readable functions for common input patterns (held keys, mouse deltas, long press, etc.) through "fuselage.h". Game code will not call CAKE directly.
